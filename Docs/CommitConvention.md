# 커밋 및 협업 규칙

형식: `type(scope): 변경 요약`. scope는 선택이며 제목은 간결하게, 본문에는 이유와 검증 결과를 적습니다. 한국어 요약을 허용합니다.

| type | 용도 |
| --- | --- |
| feat | 새 게임 기능 |
| fix | 버그 수정 |
| art | 모델·머티리얼·텍스처·애니메이션 |
| docs | 문서 |
| refactor | 동작을 유지하는 구조 변경 |
| perf | 측정 근거가 있는 성능 개선 |
| test | 테스트 및 테스트 맵 |
| build | 빌드·패키징 |
| chore | 저장소 설정 및 기타 유지관리 |

예: `feat(jelly): 착지 충격에 스프링 변형 추가`, `art(material): 젤리 표면 WPO 추가`, `docs: 에셋 네이밍 규칙 정리`.

기본 제안은 `main` + `feat/<topic>`, `fix/<topic>`, `art/<topic>`입니다. 통합 작업이 늘어나면 develop 도입을 검토합니다. 기존 원격과 브랜치가 있으면 먼저 확인하며 임의로 바꾸지 않습니다.

## 커밋 전 확인
1. 에디터에서 저장하고 Blueprint 컴파일 오류와 깨진 참조를 확인합니다.
2. 관련 맵에서 PIE로 변경한 동작을 검증합니다. 아트 변경은 전후 화면을 남깁니다.
3. status와 diff를 검토해 캐시·개인 설정·비밀정보·불필요한 대용량 파일을 제외합니다.
4. 바이너리가 LFS 대상인지 확인하고 함께 필요한 에셋·설정을 한 단위로 묶습니다.
5. 바이너리는 텍스트 병합을 기대하지 않습니다. 공동 편집 시 소유자를 조율하고 지원되는 경우 LFS 잠금을 사용합니다.

에셋 이동 시 Redirector 정리와 참조 검증도 같은 변경에 포함합니다. AI 도구가 실제 커밋 또는 푸시를 수행하기 전에는 사용자 승인을 받습니다. 원격 생성·연결 및 공개 설정도 별도 요청에 따라 진행합니다.
